## Self-check library

Each entry is defined once here and cited by the rules that need it (**Checks:** line). For every entry a rule cites: never write its ✗ patterns, run its verification commands against the files you touched, and tick its criteria before marking the change complete.

### SC-5 · Authentication & session
_Applies on auth / session / access-control changes._

**Never write:**

- ✗ Set a session cookie without `Secure` and `HttpOnly` (and `SameSite`).
- ✗ Store JWTs or session tokens in `localStorage` / `sessionStorage`.
- ✗ Skip session/token rotation after login or privilege change.
- ✗ Add an auth path that bypasses MFA, or weaken lockout / rate limiting.
- ✗ Trust a client-supplied role, `is_admin`, or permission flag.

**Verify:**

- Confirm cookies set in this change carry `Secure`, `HttpOnly`, `SameSite`.
  - Command: `grep -rniE 'set_cookie|cookies\.set'`
- Confirm no token is written to `localStorage`.
  - Command: `grep -rn 'localStorage'`

**Criteria:**

- [ ] Session rotated on login / privilege change
- [ ] No token persisted to browser local storage

### SC-6 · Secret management
_Applies on any change that may embed a secret._

**Never write:**

- ✗ Commit a literal API key, token, password, or private key in source, config, or mobile resources.
- ✗ Read a credential from a checked-in file instead of environment / a secrets manager.

**Verify:**

- Grep touched files for literal secrets; all credentials must load from env/config or a secrets manager at runtime.
  - Command: `grep -rnE '(secret|token|api_?key|password)\s*[:=]\s*["'"'"'][A-Za-z0-9/_+-]{12,}'`

**Criteria:**

- [ ] Secret scanner (gitleaks/trufflehog) clean on the diff

### SC-13 · CI/CD pipeline integrity
_Applies on workflow / pipeline changes._

**Never write:**

**Criteria:**

- [ ] CI actions pinned to immutable SHAs
- [ ] No security gate disabled in the pipeline

### SC-12 · Cryptography & transport
_Applies on crypto / TLS / key-handling changes._

**Never write:**

## Completion report — `securacy-report:v2`

Report on **controls** (the IDs like `T005.C1` above), not just rules. The Securacy CI check reads only the IDs, statuses and file locations, never free text.

**Control statuses:**

- `IMPLEMENTED` — the control is in the code. Evidence: the file and lines that implement it (you read them; you did not assume).
- `FIXED` — the control was missing and this change adds it. Evidence: the changed file and lines.
- `MISSING` — the control is not in the code. Evidence, if there is one: the file that handles this component, where the control belongs.
- `REGRESSED` — the rule's **State** shows the control in place and this change removes or weakens it. Evidence: the changed file and lines.
- `NOT_APPLICABLE` — no code in this repository implements this kind of control (it is owned elsewhere, or the infrastructure lives in another repository).

**Never pattern statuses** (`never`, the IDs like `T005.N1` above):

- `PRESENT` — specific lines do the forbidden thing themselves (a hardcoded secret, a secret printed to a log). Evidence: those lines.
- `ABSENT` — no line does it. An attack that works only because a control is missing is that control's `MISSING`, not a `PRESENT` pattern.
- `RESOLVED` — the rule's **State** marks the pattern ! and this change removes it. Evidence: the changed file and lines.

**Two kinds of run:**

- **Full sweep** (`"mode": "sweep"`): give every control and every Never pattern of every rule a status.
- **Change check** (`"mode": "diff"`): report only the controls and Never patterns the change touches: changed files that implement a ✓ control, should implement a ✗ one, or hold a ! pattern. Leave the rest out; their state carries over.

When a change adds code matching one of a rule's own **Never** patterns, report that pattern `PRESENT` with the changed lines. Set `"introduced": true` on a rule, with evidence, when the change adds code matching a cited `SC-*` ✗ pattern. Evidence `path` is relative to the repository root and `lines` is `"12"` or `"12-18"`. `component_map` maps names from the **Component map** to the paths that implement them; use only names listed there.

**Design changes** (`design_changes`): parts of the system's design that match nothing in the **Component map** or its **Design inventory**. A change check reports what the change adds (evidence: the changed lines); a full sweep reports what the repository has. Give each a `kind`, a short plain `name` (letters, digits, spaces and `. _ - / : @`, at most 60 characters) and evidence. Kinds: `external_service`, `datastore`, `message_queue`, `entry_point`, `identity`, `sensitive_data`, `cloud_resource`.

Outside CI, write the report to `.securacy/reports/securacy-report-<YYYY-MM-DD>.json` (the date you ran it) and summarise it for the user: controls in place, missing, fixed and regressed, listing every missing control of a **BLOCKING** rule.
